# TunableOp profile — rocm10-rocblas5.6

First-class named profile for the ROCm 10 / rocBLAS `5.6.0.8d1ae90e` build as
installed on this box (`/opt/rocm/core-10.0`).

It was imported as a **thin, unqualified** reference table (70 rows/rank, build
`c27e2252cc7a`, PR #5) and has since been **qualified against the build actually
loaded here**, `d05939967b5f`. The imported rows are no longer shipped: their
solution IDs were generated by a different rocBLAS build, and solution IDs must
never be reused across builds even when the version string matches. The import is
preserved verbatim under `imported` in `provenance.json`.

## Decode / MTP campaign (2026-10-14)

The 2026-10-12 campaign tuned only the prefill grid (M = 800..8192), so **every
`M <= 32` shape fell back to rocBLAS heuristics on this build** — the canonical
`../rocm7.14-rocblas5.5/` profile carries the decode (M <= 8) and MTP-verify
(M = 16/24/32) shapes, this one did not.

Built with the README recipe, service stopped:

```bash
.venv/bin/python tools/rdna2/tune_v620_fp16.py \
  --output-root $HOME/.cache/tunableop/campaign-decode \
  --batch-tokens 1 2 3 4 5 6 7 8 12 16 24 32
.venv/bin/python tools/rdna2/qualify_v620_fp16.py \
  $HOME/.cache/tunableop/campaign-decode/rocblas-d05939967b5f
```

* Tuned on GPU 0 (10 iterations, 10 ms budget per solver, numerics checked against
  FP32 in-process), then replayed on all four cards against FP32 references.
* **84/84 keys produced and 84/84 passed on devices 0-3.**
* Solver mix: 81 `Gemm_Rocblas_*`, 3 `Default` (the heuristic won for
  `tn_4096_8`, `tn_3584_7`, `tn_3584_8`).
* **Per-shape speedup over the heuristic: 1.4x to 3.6x.** The largest were the
  K=320 and K=10240 shapes (up to 3.57x at M=16, n=10240, k=320) — i.e. the
  decode path was leaving a lot on the table.

Merged into this folder: 44 prefill + 84 decode/MTP = **128 rows/rank**, key sets
disjoint. Lookup-hit proof re-run on the merged set: **128/128, 0 misses**.

Caveat: these 84 rows are raw tuned, not curated. The prefill campaign's
adopt/drop margins need a same-session heuristic-vs-current-vs-new comparison,
which was not run here. **That comparison was run on 2026-10-14** — see the next
section; the decode grid survives it, but not unexamined.

## Full-grid re-measure (2026-10-14)

`tools/rdna2/check_v620_tuning.py` reported **7 of the 14 shapes the live cache/batch
config needs as missing**. The live launcher resolves to `--block-size 1024
--max-num-batched-tokens 2048`, so the chunks that actually run are M = 1024 and 2048:
`10240x320`, `4096x2560`, `2560x1536`, `3584x2560` (M=1024) and `10240x320`, `512x2560`,
`10240x2560` (M=2048). Two deliberate mechanisms had kept them missing:
`tools/rdna2_028/tunableop_rows_pipeline.sh` tunes **only the shapes present in
`--shape-source`**, so the 26 prefill shapes the 2026-10-12 curation dropped were never
re-tested; and `curate_tunableop_rows.py` folds `Default` rows into `dropped` by design.

All 168 shapes (7 dense `(N,K)` x 12 prefill M + the 84 decode/MTP rows) were re-tuned and
then measured heuristic / current / new **in one session** — the 3 % adopt/drop margins are
meaningless across sessions, where the same rows drift 5-10 %.

**The 7 live-grid holes stay holes.** A fresh tune does not beat the rocBLAS heuristic by
3 % on any of them, so a row there buys nothing, and an explicit `Default` row would only
silence the coverage warning while pinning the shape against online tuning. The warning is
left as-is because it is telling the truth.

**The real gap was one the checker cannot express.** The launcher sets
`VLLM_RDNA_DYNAMIC_PREFILL=1`, whose chunk-cap ladder is `RUNGS = (256, 512, 1024)` with
`LPT_SHARED = 512`; `scheduler.py` sets `num_new_tokens = long_prefill_token_threshold`
whenever more than one request is eligible, so at ≥4 eligible requests a **512-token chunk**
reaches the GEMMs (256 at 8). There was no row for M = 256/512 at all, and the checker takes
only `--block-size`/`--max-num-batched-tokens`, so it cannot see that family.

| shape | M | heuristic | tuned row | delta |
|---|---:|---:|---:|---:|
| `10240x2560` | 512 | 4.33 ms | **1.22 ms** | −72 % |
| `336x10240` | 512 | 1.05 ms | **0.24 ms** | −77 % |
| `10240x2560` | 256 | 2.32 ms | **0.59 ms** | −75 % |
| `512x2560` | 512 | 0.229 ms | **0.102 ms** | −55 % |
| `2560x1536` | 512 | 0.243 ms | **0.207 ms** | −15 % |
| `3584x2560` | 800 | 0.851 ms | **0.728 ms** | −15 % |

The tuned solver reaches ~22 TFLOPS on the large-K shapes where the heuristic manages ~6.
11 rows were added and 2 shipped prefill rows were replaced by a *different* faster solver
(`10240x2560` M=1024, `2560x1536` M=3200). Two further "adopt" decisions carried the **same
solver id** as the shipped row — same-session noise, not a better kernel — and were rejected:
only adopt when the solver actually changes.

**The decode grid is deliberately left byte-identical.** 18 decode/MTP rows (M=2..8)
measured 10-77 % slower than the heuristic, which looks damning, but that region is
launch-bound: identical shape families flip sign between M=1 (row 22-58 % *faster*) and
M=2..8, on ~14 MFLOP GEMMs timed at 80-240 µs. Deleting them needs a small-M measurement
(no per-call sync, larger reps) first.

Result: **139 rows/rank** = 55 prefill + 84 decode/MTP. **139/139 matched independent FP32
on devices 0-3** and **139/139 lookup hits, 0 misses**. Rank files are identical (rank 0's
validated set); 4-7 keys per rank had picked a different solver in the same-session tune, all
within noise. Not yet measured: the end-to-end size of the 256/512 win, which only
materialises in the shared cell and so needs a mixed-load run with ≥4 eligible requests.

## Qualification campaign (2026-10-12)

`tools/rdna2_028/tunableop_rows_pipeline.sh` (PHASE=all) → `curate_tunableop_rows.py`.

* Four GPUs tuned in parallel (10 iterations, 25 ms budget per solver).
* Heuristic / current / new measured **in a single session**, then curated with the
  standard 3 % adopt and 3 % drop margins.
* Candidates: `current` = the `rocblas-d05939967b5f` capture (same build),
  `new` = fresh tune on this build.
* Decisions: **4 new, 40 current, 26 dropped of 70 shapes → 44 rows/rank.**
* Lookup-hit proof: **44/44** (`tools/rdna2_028/verify_lookup_hit.sh`, DEVICE=3).

### What the campaign actually changed

Measured back-to-back in one session:

| comparison | median | shapes beyond 3 % |
|---|---:|---:|
| heuristic vs `rocm10-rocblas5.6` | **+4.5 %** (profile faster) | 51/70 |
| `rocblas-d05939967b5f` vs `rocm10-rocblas5.6` | −0.86 % | 13/70 |

**All three candidates — the imported rows, the same-build capture, and this
curated set — measure within 0.9 % of each other**, and all are ~4 % faster than
the rocBLAS heuristic on median. The merge is therefore close to a wash; what
this campaign genuinely fixes is that the profile could not previously be
auto-selected at all (see below), and that its rows now match the loaded build.

### Measurement caveat (important for future campaigns)

* Same-session repeats agree to **~0.3 % median** (|Δ| > 3 % on 1/70 shapes).
* **Across sessions the same row set drifts 5–10 %**, which is larger than the
  3 % adopt/drop margins. Curation decisions are only meaningful when heuristic,
  current and new are captured in one session — and an apparent win must be
  re-measured back-to-back before it is believed.

## Why this profile existed as a fallback before

`profiles.json` previously recorded `lib_sha256 = c27e2252cc7a` for this profile
(a retired build). No registered profile matched the loaded library, so
`configure_tunableop` emitted

```
WARNING: no fork rows for rocBLAS build d05939967b5f ... falling back to per-user path
```

and the rows were reached only through the legacy `rocblas-<hash>/` directory.
Now:

```
TunableOp profile rocm10-rocblas5.6 auto-selected for rocBLAS build d05939967b5f.
```

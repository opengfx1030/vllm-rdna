`tools/rdna/recipes/27b-hi2-tp2.env`; row in `docs/rdna/serving.md` (port 18211, name
`q27hi2`). Choices that are not the `27b-awq` defaults:

| Setting | Value | Why |
| --- | --- | --- |
| `TP` | 2 | per-rank K of the row-parallel layers is 8704 (down) and 3072 (GDN out, attention o), both multiples of 64 (spec); 304 hi2 modules |
| `KV` | 16 GiB per rank (`--kv-cache-memory-bytes`) | one 262,144-token request needs 8 GiB (32 KiB per token per rank); 512,281 tokens fit, 1.95x concurrency at the full context |
| `SEQS` / `MAXBAT` | 8 / 2048 (derived) | c=8 keeps M <= 8 on the GEMV path; c=8 MTP=2 verify is M=24 (limit 48) |
| `CG_CAPTURE_SIZES` | `[1,2,4,8]`, `(MTP+1) x` that with MTP | FULL_AND_PIECEWISE stays on |
| `VLLM_RDNA_AR_MAX_KB` / `_ONESHOT_KB` | 256 / 256 | one-shot beats RCCL up to ~640 KiB at TP2 (sweep below); a decode all-reduce is 10 KiB per token |
| `VLLM_RDNA_HINT_FLEX_COMPUTE_MODE` | `f16` | spec default; `i8` is an A/B below |
| `FEATURES` | `prefix-caching language-model-only` | `mamba-align` was dropped: `--mamba-cache-mode` is a no-op because prefix caching already selects `align` (boot log) |
| `VLLM_CAUSAL_CONV1D_RDNA2_{FWD,UPDATE}` | 0 | as `27b-awq`; the HIP conv1d needs `state_len == width-1`, which MTP's wider state breaks |

## Decode kernel-time profile

### Method

`tools/rdna/rdna_hint_flex/decode_profile.py` boots a recipe under
`rocprofv3 --kernel-trace --selected-regions` (the venv's own rocprofv3; its attach mode
does not work on this install), then opens a 2 s recording window per cell with
SIGUSR1/SIGUSR2 -> `roctxProfilerResume/Pause` (`roctx_shim/sitecustomize.py`) while the
engine is in steady decode, and cuts the trace into steps at the
`scatter_num_accepted_kernel` launch that ends each model step
(`decode_breakdown.py`). Kernels inside CUDA graphs are recorded, which the torch
profiler does not do. Rank 0 below; rank 1 differs by < 1% except the all-reduce row (it
waits for its peer). Recording adds 5.5-7 ms per step (2.1-2.7 us per launch), so ITL
under recording is not used. The first window after boot is lost by the tool (the driver
retries). Prompts are 1024 random tokens, greedy, one cell per concurrency.

Engine ITL with the tool loaded but recording paused (image build running, not for
comparison): c=1 27.15 ms, c=2 32.39, c=4 41.31, c=8 61.39.

* At c=1 the step is 2.4x the weight floor. Weight streaming is 42% of it; the GEMV
  loses 3.4 ms to running at 372 GB/s instead of 512; **35% (9.4 ms) is launch overhead**:
  1,300 of the 2,451 launches are glue and each costs about 2 us of gap plus its own
  1-3 us.
* From c=2 on the GEMV dominates: its time grows 3.3 ms per added token (gate_up 23 us per
  token per launch on a 61 us base that corresponds to 541 GB/s), so the step costs
  27 -> 32 -> 41 -> 61 ms at c = 1 / 2 / 4 / 8 (4.9 ms per extra token) while the
  weight floor stays 11.45 ms. At c=8 the GEMV runs at 127 GB/s. [inference] a verify
  step of MTP=2 (M=3 per sequence, 24 rows at c=8) pays that per-row cost.
* The all-reduce is 1.1-1.8 ms per step in 129 launches of ~8.5 us, part of it waiting
  for the other rank; 256 KiB one-shot is already in use.

## LM head rows 9-32 and the memory gap (integration branch)

**LM head.** `rocm_unquantized_gemm_impl` sent 9 to 32 rows to rocBLAS although
`gemv_f16_rdna2` serves 1 to 32 rows (`TORCH_CHECK(M >= 1 && M <= 32)`, templates for
16/24/32) and `tests/kernels/quantization/test_gemv_f16_rdna2.py` already checks M = 1, 3,
8, 9, 12, 16, 17, 24, 32 against `linear`. `VLLM_RDNA_LM_HEAD_GEMV_MAX_M` (default 8 = the
old behaviour, so every other recipe is unchanged; the `27b-hi2-tp2` recipe sets 32) now
lets a `ParallelLMHead` use the gemv up to that many rows; every other dense layer keeps 8.
Tests (`tests/model_executor/layers/test_rocm_unquantized_gemm.py`): the row-cap selection
per layer class, the dispatch at 8, 9, 12, 32, 33 rows with a cap of 8 and of 32 (CPU, the
kernel mocked: 14 passed), and a real-kernel check at 9 to 32 rows that skips off gfx10x.
The speed effect ran as the scoreboard arms `mtp2-nofix` (cap 8) and `mtp2-lmfix` (cap 32),
MTP=2 and nothing else: output tok/s at 1k/512 c=1, 2, 4, 8 are 55.3 / 75.2 / 82.0 / 98.6
with cap 8 and 55.2 / 75.2 / 86.2 / 100.4 with cap 32, ITL p99 at c=4 118.8 against 92.6 ms.
The cap matters from 3 concurrent requests (9 rows at MTP=2); the c=8 ITL p99 stays at about
1.66 s. The real-kernel unit test needs a GPU and was not part of this change's CPU
verification. The 12-row gemv time is unmeasured on its own; the only measured numbers are
rocBLAS 10.42 ms at 12 rows and the gemv 2.93 ms at up to 6.

**The 0.78 GiB.** What "Model loading took" counts is read from the code: on ROCm
`get_current_memory_usage` is `empty_cache()`, `reset_peak_memory_stats()` and
`max_memory_allocated()`, so the figure is the growth of live torch allocations around
`load_model`, not driver-level memory or allocator cache. The target model drops the
checkpoint's `mtp.*` tensors (`WeightsMapper(orig_to_new_prefix={"mtp.": None})` in
`qwen3_5.py`), so the BF16 MTP layer is **not** loaded at MTP=0 and does not explain the
0.78 GiB (its size, 0.79 GiB, is a coincidence).

**Resolved by the scoreboard boot logs (2026-11-15).** The gap is mostly the GDN state
arenas. `Model loading took` is 7.46 to 7.47 GiB in the arms without
`VLLM_RDNA_GDN_DECODE_INPLACE` (`base`, `residual`, `attn`, `gemv`, `tunable`) and 6.79 to
6.80 GiB in the arms with it (`gdnglue`, `stack`, `final`): the switch skips
`_init_gdn_state_arenas()`, and the arenas hold (`max_num_seqs` x (`num_spec` + 1) + 1)
rows of about 1.53 MiB in each of the 48 GDN layers, 0.65 GiB at MTP=0 `[derived]`. About
0.11 GiB (6.79 against the 6.68 accounted) stays unexplained. At MTP=2 the arenas have 25
rows (1.8 GiB `[derived]`): 9.03 GiB without the switch (`mtp2-nofix`, `mtp2-lmfix`) and
7.19 GiB with it (`final-mtp2`), so the drafter adds 0.40 GiB, about its one layer (0.395
GiB per rank). No second copy of `embed_tokens` / `lm_head` stays resident, which the first
version of this note had guessed from the 1.57 GiB it saw without the switch; there is no
1.18 GiB to win back.

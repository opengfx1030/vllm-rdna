# rdna_extras → v0.31.0 port: decisions, open questions, test plan

Branch: `rdna_extra/v0.31.0` = upstream `v0.31.0` + topic commits porting
`rdna_extras@c6d99ca305`. It is named `rdna_extra/…` (no `s`), like
`rdna_extra/v0.29.0` and `rdna_extra/v0.30.0`, because git cannot hold both
`refs/heads/rdna_extras` and `refs/heads/rdna_extras/v0.31.0`.

**Nothing here has run on a GPU yet.** The port was done on a Mac with static
checks only (see "What was verified"). Test target: the 8× V620 build server
`par1-cs25` (`192.168.1.84`), venv-7.14.0, when it is free.

## How the port was built

- `rdna_extras` = `v0.28.0` + upstream main up to `e25c586b90` (2026-08-23,
  merged in by fork PRs) + 408 fork-only commits (19 merges). Two of those are
  upstream backports already in v0.31 (#55450, #57145) and were dropped.
- The fork's net delta was merged onto `v0.31.0` once (3-way, base
  `e25c586b90`): 102 conflicting files (58 content, 28 add/add, 15 rename,
  1 modify/delete), resolved by hand, then split into 33 commits by topic and
  by each file's dominant original author. Intermediate commits are not
  guaranteed to build; the branch tip is the resolved tree.
- Authorship: each commit is authored by the dominant original author of its
  files (by changed lines); every other original author and existing
  `Co-authored-by` trailer is carried as a co-author. Agent identities
  (`agent`, `kletorch`, `Cursor Agent`, `Claude`, Codex, MiniMax, Sisyphus,
  opencode, …) map to BlivionIaG. Each commit lists the original SHAs it
  carries, so history stays traceable on `rdna_extras`.
- qwen4_exp: upstream landed its own Qwen3.8 Flash-Next (#53896, 2026-08-31).
  The fork carried a port of an earlier revision of it (Aron Hsiao,
  `5765f57b4c`). The 28 add/add files were 3-way merged with **upstream
  `e126687a9a` (#53896) as base**, so only the fork's real deltas were
  replayed.

## Open questions (need a decision)

1. **PLE CPU offload (biggest).** Upstream v0.31 offloads the PLE n-gram table
   itself: `EngramConfig.cpu_offload=True` (**default**) keeps it in pinned
   host memory with UVA lookup (#54371, #57497 "[ROCm] PLE n-gram table CPU
   offload"). The fork used a CPU sidecar process (`vllm/v1/ple_offload/*`,
   `PleOffloadLayer`, `VLLM_PLE_CPU_OFFLOAD`, `VLLM_PLE_QUANT_DIR` int4/fp8
   shards, `VLLM_PLE_DISK_OFFLOAD_DIR`).
   - Port: `qwen4_exp/amd/ple_layer.py` = upstream + the fork's RDNA2 compute
     hooks only. The sidecar code is kept but **not wired**;
     `VLLM_PLE_CPU_OFFLOAD=1` now fails at worker init with an explicit
     message instead of silently doing nothing.
   - Decide after T-PLE: (a) adopt upstream UVA and delete the sidecar,
     (b) re-wire the sidecar as an alternative embedding class, or (c) keep
     both. Note the int4/fp8 quantized table (`VLLM_PLE_QUANT_DIR`) has no
     upstream equivalent; upstream has FP8 PLE weights via the quant config.
2. **KV-cache grouping for Qwen4Exp.** The fork grouped Qwen4Exp caches with a
   CSA+linear path in `kv_cache_utils.py` (from Aron's pre-merge port; it never
   existed in any upstream release). Upstream v0.31 handles these layouts with
   its generic "packed KV cache groups". **Took upstream wholesale**; the CSA
   path is gone. Must re-validate memory, prefix caching and correctness
   (T-QSA, T-PREFIX).
3. **QSA prefix-cache ring fix.** The fork's `e45dd5cb2` made
   `CircularBufferManager.find_longest_cache_hit` return ring-aligned hits.
   Upstream instead skips non-prefix-cacheable scratch groups (the QSA ring)
   when reconciling hits (#57145 + coordinator). **Took upstream**; the fork's
   regression test was dropped. Must confirm hits still happen (T-PREFIX).
4. **QSA prefill scoring bound (fork PR #15, +18 % prefill).** The fork passed
   `num_prefills` as a "long-prefill present" flag and `max_seq_len` to bound
   `qsa_select_paged_tokens`. Upstream now has real `num_prefills` /
   `max_seq_len` fields and its own indexer workspace work (#54915, #57105).
   The fork's duplicate fields were dropped. Re-measure 8×16k/1k (T-QSA-PERF).
5. **Launchers in `scripts/` vs `tools/`.** Upstream #58572 removed `scripts/`
   and moved its own auxiliary files to `tools/`; git suggested moving the
   fork launchers too. Kept them in `scripts/` (AGENTS.md and box workflows
   call `scripts/…`). Move to `tools/`?
6. **Non-gated fork changes that also affect CUDA (pre-existing on
   rdna_extras).** Need ROCm/gfx10x gating before any upstreaming:
   - `config/vllm.py`: `Qwen3_5ForCausalLM` / `Qwen3_5MoeForCausalLM` in the
     breakable-cudagraph architecture set auto-enable
     `VLLM_USE_BREAKABLE_CUDAGRAPH` on every platform.
   - `gdn_attn.py`: `use_static_state_buffers` + state arenas apply to all
     platforms (any cudagraph mode). As a consequence upstream's GDN metadata
     reuse across KV groups (#58762) is now **disabled whenever static state
     buffers are on**, on CUDA too.
   - `platforms/__init__.py`: generic `torch.version.hip` ROCm fallback.
7. `RDNA2W4A16MoEExperts` is not in `make_wna16_moe_kernel`'s
   `allowed_experts` (same on rdna_extras): confirm the Flash-Next AWQ MoE path
   does not reach that assert (T-MOE).
8. Debug knobs kept from the fork, cleanup candidates: `VLLM_MOE_NAN_DEBUG`,
   `VLLM_LAYER_NAN_DEBUG` (qwen4_exp model), `VLLM_TRACE_PREFIX_CACHE`,
   `VLLM_DEBUG_PREFIX_HIT`, `VLLM_NO_PARTIAL_HASH` (coordinator),
   `VLLM_BT_DEBUG` (block table), `VLLM_MAMBA_COPY_DEBUG`,
   `DBG_VLLM_STEP_TIMING` (V2 runner; upstream now has its own `step_timing`).

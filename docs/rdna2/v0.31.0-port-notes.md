# rdna_extras → v0.31.0 port: decisions, open questions, test plan

Branch: `rdna_extra/v0.31.0` = upstream `v0.31.0` + topic commits porting
`rdna_extras@c6d99ca305`. It is named `rdna_extra/…` (no `s`), like
`rdna_extra/v0.29.0` and `rdna_extra/v0.30.0`, because git cannot hold both
`refs/heads/rdna_extras` and `refs/heads/rdna_extras/v0.31.0`.

**Nothing here has run on a GPU yet.** The port was done on a Mac with static
checks only (see "What was verified"). Test target: the 8× V620 build server
`par1-cs25` (`192.168.1.84`), venv-7.14.0, when it is free.

## How the port was built

- `rdna_extras` = `v0.28.0` + upstream main up to `e25c586b90` (2026-08-23,
  merged in by fork PRs) + 408 fork-only commits (19 merges). Two of those are
  upstream backports already in v0.31 (#55450, #57145) and were dropped.
- The fork's net delta was merged onto `v0.31.0` once (3-way, base
  `e25c586b90`): 102 conflicting files (58 content, 28 add/add, 15 rename,
  1 modify/delete), resolved by hand, then split into 33 commits by topic and
  by each file's dominant original author. Intermediate commits are not
  guaranteed to build; the branch tip is the resolved tree.
- Authorship: each commit is authored by the dominant original author of its
  files (by changed lines); every other original author and existing
  `Co-authored-by` trailer is carried as a co-author. Agent identities
  (`agent`, `kletorch`, `Cursor Agent`, `Claude`, Codex, MiniMax, Sisyphus,
  opencode, …) map to BlivionIaG. Each commit lists the original SHAs it
  carries, so history stays traceable on `rdna_extras`.
- qwen4_exp: upstream landed its own Qwen3.8 Flash-Next (#53896, 2026-08-31).
  The fork carried a port of an earlier revision of it (Aron Hsiao,
  `5765f57b4c`). The 28 add/add files were 3-way merged with **upstream
  `e126687a9a` (#53896) as base**, so only the fork's real deltas were
  replayed.

## Decisions and remaining open questions

1. **PLE CPU offload — decided: upstream offload + our fixes on top (to be
   tested).** Upstream v0.31 offloads the PLE n-gram table itself:
   `EngramConfig.cpu_offload=True` (**default**) keeps it in pinned host memory
   with UVA lookup (#54371, #57497). `qwen4_exp/amd/ple_layer.py` = upstream +
   the fork's RDNA2 compute hooks only. The Flash-Next recipes
   (`tools/rdna/recipes/flashnext*.env`) no longer set
   `VLLM_PLE_CPU_OFFLOAD` / require `VLLM_PLE_QUANT_DIR`. The sidecar code
   (`vllm/v1/ple_offload/*`) stays in tree, unwired; `VLLM_PLE_CPU_OFFLOAD=1`
   fails at worker init with an explicit message. Still open: which fork PLE
   fixes are needed on top of upstream once T-PLE runs (e.g. int4/fp8 table
   quantization from `VLLM_PLE_QUANT_DIR` has no upstream equivalent), and
   whether to delete the sidecar afterwards.
2. **Qwen4Exp KV grouping — answered: nothing to carry.** The fork's CSA+linear
   grouping in `kv_cache_utils.py` came from Aron's port of a pre-merge
   revision of upstream's own #53896 and never shipped in an upstream release.
   Upstream replaced it with the generic packed KV groups
   (`_get_packed_kv_cache_groups`: mixed page sizes packed per block, Mamba /
   circular-buffer state buckets fitted into the block) and kept the
   prefix-boundary validation. Only verification is needed: KV memory /
   max concurrency no worse than rdna_extras, prefix caching correct (T-PREFIX,
   T-KVMEM).
3. **QSA prefix-cache ring fix** (`e45dd5cb2`) replaced by upstream's skipping
   of non-prefix-cacheable scratch groups when reconciling hits. Verify
   (T-PREFIX).
4. **QSA prefill scoring bound (fork PR #15, +18 %)** replaced by upstream's
   real `num_prefills` / `max_seq_len` and indexer workspace work (#54915,
   #57105). Re-measure (T-QSA-PERF).
5. **Launchers — done: moved to `tools/rdna/`** (`serve_rdna.sh`,
   `serve_gfx1030_*.sh`, `rdna_launcher_common.sh`, `bench_report.py`,
   `sync_remote_to_local.sh`, `recipes/*.env`). Not `tools/recipes/`: upstream
   already uses that for its JSON recipe tooling. The default `VLLM_TREE` is
   now two levels above `tools/rdna/`; drivers in `tools/rdna2_028/` and docs
   were updated. Historical `bench_results/` records keep the old paths. The
   parent project's AGENTS.md still says `scripts/serve_gfx1030_*.sh` for the
   0.28 tree; use `tools/rdna/…` on this branch.
6. **Upstream behavior everywhere, fork behavior RDNA-gated — done** (see
   "RDNA gating" below).
7. `RDNA2W4A16MoEExperts` is not in `make_wna16_moe_kernel`'s
   `allowed_experts` (same on rdna_extras): confirm the Flash-Next AWQ MoE path
   does not reach that assert (T-MOE).
8. Debug knobs kept from the fork (all env-gated, off by default), cleanup
   candidates: `VLLM_MOE_NAN_DEBUG`, `VLLM_LAYER_NAN_DEBUG`,
   `VLLM_TRACE_PREFIX_CACHE`, `VLLM_DEBUG_PREFIX_HIT`, `VLLM_NO_PARTIAL_HASH`,

## RDNA gating

Policy: on CUDA, CDNA, CPU and every other platform the branch behaves like
upstream v0.31. Fork behavior in shared code runs only on ROCm RDNA.

- Gate: `vllm/platforms/rdna.py` — `on_rdna_family()` = ROCm and (gfx10x or
  RDNA3/4, i.e. `on_gfx10x() or on_rdna()`), matching AGENTS.md's
  `_RDNA_ARCHS = _ON_GFX10X or _ON_GFX1X`; `on_rdna2()` = gfx10x. Memoized, and
  never imports `vllm.platforms.rocm` off ROCm. Dynamo-traced hot paths read it
  once at import (`_ON_RDNA`) or in `__init__`.
- Note: upstream `on_rdna()` is gfx11/gfx12 only. The fork's EXL3 fp16 cast
  used it and therefore never fired on gfx1030; it now uses
  `on_rdna_family()`.
- Kernels that exist only for gfx1030 (`causal_conv1d_*_rdna2`, GDN HIP prefill)
  use `on_rdna2()`.
- Three places where upstream already has RDNA3/4-specific decisions keep
  upstream for gfx11/gfx12 and apply the fork change to gfx10x only:
  `use_rocm_custom_paged_attention` (FA-RDNA2 block/head relaxation, needs
  `VLLM_USE_RDNA2_FA=1`), `num_compute_units` (×2), RMSNorm IR priority
  (`vllm_c, native`).

## W4A8 prefill (opt-in): validated, recommended for prefill-heavy serving

`VLLM_RDNA2_W4A8_SDOT4=1` (recipe knob `W4A8=1`) runs the dense W4A16 prefill GEMMs
(M >= 33) with int8 activations on `v_dot4` (`csrc/rocm/w4a8_sdot4_rdna2.cu`); decode stays
W4A16 and ineligible shapes fall back inside the C++ entry. It stays **opt-in**.

Qwen3.8-27B AWQ, TP=4, FULL_AND_PIECEWISE, 4x V620 (2026-10-09, same tree/GPUs/cache):

| Cell | W4A8 | Prefill tok/s | Decode tok/s/req | TTFT s | ITL med ms |
|---|---|---:|---:|---:|---:|
| 1k/512 c=1 | off / **on** | 1113 / **1417** | 42.1 / 43.3 | 0.92 / **0.72** | 23.7 / 23.1 |
| 1k/512 c=8 | off / **on** | 250 / **335** | 22.1 / 23.6 | 4.10 / **3.05** | 38.6 / 37.3 |
| 16k/1k c=1 | off / **on** | 885 / **1102** | 37.3 / 38.2 | 18.51 / **14.86** | 26.8 / 26.2 |
| 16k/1k c=8 | off / **on** | 400 / **496** | 6.4 / 7.4 | 40.95 / **33.03** | 55.0 / 54.0 |

Greedy output byte-identical to W4A8 off, PPL 4.90 vs 4.94, prefix PASS, 0 faults; the fast
path fires on all ranks for all 5 dense projection shapes. One run per arm (not
noise-bounded). Not yet validated: MoE W4A8 in serving (Flash-Next), backlog.

### Fused hyper-connection prefill mix (2026-10-10, agent V)

Flash-Next runs 97 HC mixes per forward (two per layer plus the final one).
For M > 8 tokens `rdna_hc_mix` ran rocBLAS down `[M,10240]x[10240,336]`
(rows padded to 64 for the tuned TunableOp rows), a Triton silu, rocBLAS up
`[M,320]x[320,10240]` writing an `[M,10240]` gate, and a Triton gate mix
reading it back. `csrc/rocm/hc_prefill_rdna2.cu` replaces that:

- `rdna_hc_up_gate_mix_prefill`: silu + up GEMM + sigmoid + gated mean in one
  kernel. A block owns BM tokens x BH hidden columns and computes the 4*BH
  gate columns feeding them (rows `c*H + h` of `W_up` for the four streams),
  so the gate never leaves registers; silu(x/4) is applied while staging dai
  into LDS. v_dot2_f32_f16, wave32, k-pair-major LDS tiles (tokens read with
  ds_read_b128, broadcast across the 16 column lanes), register prefetch of
  the next K slab. 22-25 TFLOP/s for the up GEMM it absorbs; rocBLAS gets
  17-23 for the bare GEMM.
- `rdna_hc_mix_prefill`: split-K HIP down GEMM (fp32 atomic accumulator,
  ~72 blocks) feeding the fused kernel, which also writes the fp16 dai the
  injection logits are sliced from. 1.1-1.2x rocBLAS at M = 512-2048 and
  ~1.9x at M <= 128 (rocBLAS fills too few CUs there). The atomic order makes
  the down projection non-deterministic at fp32 rounding level.

`VLLM_RDNA_HC_PREFILL_FUSED`: 2 (default: both kernels), 1 (rocBLAS down +
fused kernel), 0 (torch). Used only when the gfx1030 ops exist and the GPU is
gfx10x. Decode (M <= 8) keeps the T46 fused GEMV kernels.

never fused anything: it ports the five Triton glue kernels (rmsnorm, silu,

## Replay-copy wrapper removed (2026-10-10)

RDNA now uses upstream CUDA-graph capture and replay. Removed:

- the RDNA paths in `CUDAGraphWrapper` (cloned activation inputs per capture
  size, replay copies, strong output refs, the NaN scrub, the shared-buffer mode
  from `dc9e536f13`) and the RDNA `make_copy_and_call` staging,
  `should_copy_cudagraph_inputs` and non-contiguous sym inputs (`backends.py` and
  `caching.py` are upstream again);
- the split of piecewise graphs at the TP collectives. The all-reduce is captured
  inside the pieces, as upstream does. The opaque TP collective ops stay, so
  Dynamo does not trace into the communicator;
- strong refs in breakable eager breaks (upstream weak refs again);
- the capture flags `rdna2_set_graph_capturing`/`rdna2_freeze_capture_persist`,
  `rdna2_immortal_zeros`, `rdna2_keep_if_capturing`, and the unused
  `vllm/utils/rocm_graph_keepalive.py`. `csrc/rocm/rdna2_scratch.cuh` keeps only
  the grow-only split-K scratch of FA-RDNA2 (op-internal; a grown buffer is
  retired, never freed).

The real remaining cause was the GDN opaque forward. It wrote into a persistent
buffer sized to `max_cudagraph_capture_size` and allocated inside the eager break.
With a capture ladder above 8, warmup died in
`assert_size_stride(... 512==16)`. The output is now a plain `empty_like`
allocated before the eager break, i.e. in the graph pool, which is what breakable
replay requires.

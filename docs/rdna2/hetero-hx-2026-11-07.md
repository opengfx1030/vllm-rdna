## 1. What hx is, in one paragraph

Per MoE layer the hub (W7800 in stage 1) pushes the activation rows of the pairs whose expert lives on a V620 expert
server straight into that server's VRAM with posted peer-to-peer stores, then writes one sequence-numbered flag. The
server polls the flag in its own VRAM, runs its experts, pushes the partial output rows into the hub's reply region and
writes its flag; the hub waits for the flags in a fixed order and adds the partials in fp32 in a fixed order. No PCIe
reads happen while waiting, every wait has a device-side timeout counted in wall-clock ticks, and one sticky abort word
plus a first-claimer record turn a lost peer into a loud failed step (NaN output, abort record, process exit) instead of
a hung GPU. All state that changes per step (epoch, row count, ids, descriptors) lives in device memory, so the kernels
run unchanged inside CUDA/HIP graphs. The kernels are arch-neutral HIP (wave32 on gfx1030 and gfx1100) with no torch
dependency; `hx_ops.cu` wraps them into the `_rocm_C` torch ops and `tools/rdna/hetero_moe/hx_loopback.cpp` calls them
directly.

## 3. Wire protocol as built

Appendix C of the spec is the contract; the numbers below are what the code implements (layout for `nslots=2`, four
servers, 2048 rows): slot stride 10,608,640 B, server inbox 21,221,376 B, hub reply region 83,890,176 B, `y_stride`
10,485,760 B. `HX_VERSION=1`, `HX_MAGIC=0x48585F50524F5431`, `HX_PAGE=4096`, sequence `seq = epoch*64 + layer + 1`
(serial-number order, so epoch wrap is harmless), ring entry `<QQIHHQ` (32 B) after a 64 B header.

Clarifications and additions to Appendix C (all agreed or to be sent to the spec owner, section 11):

- **Handshake files** use the device ids of the plan, not indices: `srv_<id>.json` (published only after weights are
  loaded, the self-test passed and the graphs are captured), `hub_<id>.json`, `ack_<srv>_<hub>.json`, `ring_<hub>.bin`
  under `/dev/shm/hx_<plan_id>/`. A server that lives in the directory of another plan id never finds its files, which is
  how `wrong-plan` ends in a bounded timeout (and the header check catches a plan hash mismatch on a live link).
- **Host abort word** at inbox control offset `0xF00` (`HX_CTRL_HOST_ABORT`): when the pidfd watcher sees a peer die,
  the host pokes it into the local control page; a spinning wait sees it within about 100 µs and ends with phase 8
  (`HX_PH_HOST`) without a second claim.
- **Ring entries carry an opcode** (`HX_OPCODE_MOE=1`; room for the stage-2 opcodes) next to the bucket and row count.
- **Abort record** (one 64-bit word, written once by the first claimer): valid bit, live bit, phase (bits 4-7: 1 dispatch,
  2 combine, 3 server wait, 4 server begin, 5 header mismatch, 6 push, 7 plan, 8 host), peer byte, waited ms (16 bit,
  saturating), low 32 bits of the sequence. `status[HX_ST_LIVE]` is refreshed once per second by a waiting
  block and **is not cleared after a successful wait** (it shows the last slow wait; informational).
- **Receive buffers are always uncached VRAM** (section 4). `hx_alloc` kinds are 0 coarse, 1 uncached, 2 fine-grained
  with no silent fallback; default `uncached` (`VLLM_HX_ALLOC`).
- **`hx_k_srv_wait` copies the request rows into cached workspaces** (`ctx.x_ws`, `ctx.w_ws`) after the flag is seen, so
  the server's grouped GEMMs read cached memory; the wire layout is unchanged.
- **Per-layer pair counters** (hub, optional): `HxHub.create(..., layer_stats=True)`, `hub.layer_stats()` returns an
  int64 `[nlayers, 3]` tensor (hub, cold, spill), `hub.reset_layer_stats()`; zero cost when off (the ctx field is null).

## 4. Kernels and memory model

Kernels (grid sizes are launch-time, from the bucket table; all state comes from the ctx tensor):

| Kernel | Side | What it does |
|---|---|---|
| `hx_k_begin_step` | hub | `epoch++`, writes the 64 B header into every server inbox, flag last with release semantics. |
| `hx_k_dispatch` | hub | spill rule and per-server masked ids, pushes x / ids / weights into each inbox slot; the flag follows the last block's system fence. |
| `hx_k_combine` | hub | waits the reply flags in server index order, adds hub partial + server partials in fp32 in that fixed order, writes fp16; NaN-poisons on abort. |
| `hx_k_srv_begin` | server | waits the header, checks magic, plan hash, epoch, row count, bucket, opcode, version against the host descriptor (abort phase 5, field in the peer byte). |
| `hx_k_srv_wait` | server | waits the request flag, widens ids int16 to int32, copies x and w into the cached workspaces. |
| `hx_k_srv_push` | server | y rows into the hub reply slot, system fence, flag. |

Memory model, as established on hardware (T1, section 8.2) and used by the kernels:

- Peer stores are posted writes into the receiver's **uncached** VRAM; a peer store never invalidates the owner's L2,
  so only uncached memory is safe for polled flags and payload. T1 measured it: the polled flag in uncached memory is
  always seen (`coherent=yes`), in coarse and in fine-grained memory it is never seen (`timeouts_total=8`).
- Payload stores, then `__threadfence_system()`, then one release store of the flag; the receiver polls with
  system-scope acquire loads and `s_sleep(2)` in its own VRAM. A wait is never unbounded: the budget is in
  `wall_clock64()` ticks, with the rate calibrated against the host clock at init (`hx_calibrate`; measured 99.98 MHz on
  gfx1030, T1) and refused if it is not within 5 % of the expected rate.
- Timeouts and aborts: the first block to time out claims `abort_word` (atomic CAS) and writes the record; every other
  wait ends on the abort word without a second record; combine writes NaN so the failure cannot be mistaken for data.
- Graph safety: epoch, T, bucket, descriptors and all tables are read from the ctx and from device tables at run time;
  the Python facade launches the same kernels with the same arguments per bucket, so a replay behaves like an eager call.
- Multi-block kernels do not wait on each other except through the flag/counter protocol of the last block
  (`HX_MAX_*` bounds are static asserts); co-residency is not needed (no kernel waits on another block of its own grid;
  confirmed by the independent review of `hx_core.cuh`, section 10).

## 5. Host side

- **`ctx.py`**: allocates the inbox / reply / workspaces (`alloc_exported`: `hx_alloc` + IPC handle bytes), opens the
  peers' handles (`hx_open`, `hx_view`), calibrates the clock, builds the context image (`hx_ctx_new/set/get`) and
  registers it on the device; `HxHub` and `HxServerCtx` own the per-process device state.
- **`rdv.py`**: file rendezvous with atomic publish (write to a temp name in the same directory, rename), handshake and ack
  files, `PeerWatcher` (one pidfd per peer, epoll; `stop()` is idempotent and closes every descriptor) and the host abort
  poke into the control page. A peer death becomes an abort record in 61 to 126 ms (section 8.3).
- **`ring.py`**: shared-memory ring from hub to servers; the hub model runner announces every forward (`post_step`)
  before its kernels are launched, so a server knows the bucket in time to replay the right graph.
- **`hx.py`**: the facade `HxHub` the hub method uses: `create`, `begin_step`, `dispatch`, `combine`, `status`,
  `layer_stats`, `close`; the same code path serves eager and graph-captured use.

## 6. Expert server

```text
python -m vllm.distributed.hetero_moe.server --plan P --device-id exp0 [--model CKPT] [--expect-bus ce]
    [--ready-file F] [--buckets 3,6,12,24,48] [--max-rows 2048] [--nslots 2] [--wait-ms 2000]
    [--begin-wait-ms 600000] [--hub-timeout 7200] [--alloc uncached] [--no-graphs] [--no-selftest] [--synthetic]
```

Boot: parse the plan, check the GPU against `--expect-bus`, load the resident experts of its device from the checkpoint
(or synthetic weights), allocate and export the inbox and workspaces, run the self-test, capture one graph per bucket,
publish `srv_<id>.json`, wait for the hub's `hub_<id>.json`, handshake and ack, then loop: ring entry, `srv_begin`,
`srv_wait`, grouped expert GEMMs, `srv_push`, per layer. Rows above the largest captured bucket run eager. Exit codes:
0 clean (the hub closed), 3 abort or peer death (the record is printed), 4 setup failure. `--synthetic` skips weights
(T5 `faults`).

The 11 FAIL rows of the table are four `bw1m` fan-in rows (one per configuration, deterministic; every link is Gen4 x16
with 256 B MaxPayload per `lspci`, so the shortfall looks like a hub-ingress limit [INFERENCE]; to be re-measured with
four senders into the W7800) and seven `poll` rows with `slow_gt100x_median=1`: one 1.0 to 1.8 ms outlier per 200k
round trips, never a stale or out-of-order read. Follow-up (`~/w4a8_runs/t1_evict`, `t1_sleep`: six poll runs, both
directions, 12 measurements per variant, three of the runs with `--sleep 1`): the KFD `evicted_ms` of every probe
process stayed 0, so these are not queue evictions; the `relaxed` variant never had a round trip above 57.3 us; the
`acquire` variant had a maximum of 0.5 to 1.2 ms in 9 of 12 measurements and the `volfence` variant in 8 of 12 (1.0 to
1.7 ms in 6 of 12); p50 and p99 are identical in the three variants (12.3 and 24.4 us). A per-poll acquire load or
fence therefore costs a rare stall of about a millisecond (about one per run of 200k round trips), polling relaxed does
not. The production loop (`hx_wait_flag`) polls with acquire loads plus `s_sleep(2)`; the 80k layer exchanges of the
loopback bench (worst layer 120 us) are too few to have caught one [INFERENCE: about 0.4 expected]. Recommended next
change, to be proven by T1 and the soak: poll with relaxed loads and execute one system-scope acquire fence after the
flag is seen (same ordering, no invalidate per poll).

| Case | Result |
|---|---|
| `kill-hub` (hub SIGKILL) | PASS: servers exit 3 within 1.55 s |
| `kill-server` | PASS: hub exit 3 after 0.38 s, the other servers within 1.62 s |
| `freeze-server` (SIGSTOP) | PASS: hub exit 3 after 2.17 s (device wait budget 2 s), servers within 3.24 s |
| `freeze-hub` (hub SIGSTOPs itself between two layers) | PASS: servers exit 3 within 3.38 s (phase 3; the harness runs the servers with `--begin-wait-ms 3000`) |
| `wrong-plan` | PASS: the hub fails after the 20 s connect timeout (exit 4, 27 s wall) because the plan-id directories never meet; the servers stay up and exit 0 on SIGTERM. This is a bounded handshake timeout, not a 5 s abort |

Two bugs came out of the first GPU start of the Python server. (1) `torch.ops._rocm_C.hx_alloc` has no tensor argument and
was registered for the CPU key only; such an op is never dispatched to a CPU kernel (`no fallback function is registered
for schema _rocm_C::hx_alloc`); it is now registered like the other tensor-less ops. The CPU tests never saw it because
with `HIP_VISIBLE_DEVICES=` the dispatcher falls back to CPU. (2) A server waiting for the hub died with exit code -15
on SIGTERM (first `wrong-plan` run): the sigwait thread cannot stop threads created before the mask (torch, HIP runtime)
from taking the default action. `_start_signal_thread` now uses a wakeup fd with a no-op handler, and `connect_hub`
returns `False` when a stop arrives while it waits (CPU test with a fork and an older thread).

## 9. Runbook

Rules first: V620 steps need `HxServer.slotA` (HIP 1-4 = buses ce, d3, d8, db); W7800 steps need `<owner>.w7800cb`
(HIP 0 = bus cb; HIP 5 is forbidden); rocm-smi indices are KFD order, always resolve HIP to PCI bus (the scripts do);
every GPU command sets `HIP_VISIBLE_DEVICES` on its own line; measured windows use `hx_quiet_begin`; builds under
`~/w4a8_runs/audit/build.lock`, `MAX_JOBS` <= 8; W7800 Python processes use `~/Apps/vllm/venv-7.14.0` with `PYTHONPATH`
at an exact-SHA tree whose `_rocm_C` is a fat `gfx1030;gfx1100` build containing the hx ops and which carries the

## 10. Risks and open items

- **gfx1100 behaviour**: polled-flag visibility, uncached allocation, the tick rate of `wall_clock64` and
  `hipIpcOpenMemHandle` between a W7800 and a V620 were unmeasured before 8.6; they now work (single-GPU loopback, T1,
  soak, T5), apart from the open items below. The remaining architecture-specific risk is the one soak mismatch (8.6):
  until it is explained, run the soak of section 9 step 3c several times (and as 1e7 exchanges) before any long model
  run on the W7800.
- **1 MiB fan-in**: 22.6 GB/s with three V620 senders and 14.5 GB/s with four senders into the W7800 against the 24 GB/s
  gate, in every configuration (8.2, 8.6); decode rows are KiB-sized, so this bounds prefill-sized steps only (a 2048-row
  step moves about 3.3 ms of transport per layer in the bench) [INFERENCE: the effect on prefill is not measured end to end].
- **Millisecond poll stalls** with per-poll acquire loads or fences (section 8.2): the production wait loop is of that
  kind; harmless for correctness (never stale), about 1 ms per 200k polls at worst; the relaxed-poll plus one-fence
  variant is the recommended follow-up and the `slow_gt100x_median` rows stay FAIL in the T1 table until then.
- **Exchange through the Python stack** (the open item of the latency): 86 / 99 / 134 us per layer against 36 / 64 / 99
  us in the torch-free loopback, +50 / +35 / +35 us per layer (+2.4 / +1.7 / +1.7 ms per 48-layer step). Per step or per
  layer is not decomposed (fit the step time over 12 / 24 / 48 layers, or `rocprofv3 --kernel-trace` of one graph on the
  hub and a server and count the nodes); candidate: the host-driven wake of the server graph (spec C.6, R4).
- **Hung hub host between steps**: servers have only `--begin-wait-ms` (600 s) to notice a hub that is stopped but not dead
  (`freeze-hub`, hub SIGSTOP); a dead hub is detected in under 100 ms by pidfd. A heartbeat would close this
  [INFERENCE: cheap to add if the user wants a bounded answer].
- **Host abort poke while a spin kernel runs** relies on the copy queue; worked in all loopback kill tests (61 to 126 ms).
- **Self-test tolerance** of the server is not calibrated on hardware yet.
- **Independent read-only review of `hx_core.cuh` / `hx_ops.cu`** (a separate reviewer, nothing built or run): no
  data-corrupting bug on the normal path; payload-before-flag, poll, slot reuse, bounded waits, graph replay and combine
  arithmetic judged safe; the W7800 as a sender is unproven (T1 3b and the soak 3c settle it; a negative control with the
  fence removed is advisable). Findings, none fixed yet: (1) in `hx_k_dispatch` a plan error claimed by block 0 can stop
  later blocks before they take their ticket, so the layer is not always published and the servers then time out
  (confusing diagnosis, still loud on the hub; the CPU model always publishes); (2) `status[HX_ST_LIVE]` and the record
  live in coarse ctx memory read by a DMA copy while the kernel spins, so the live word may stay invisible until the
  kernel exits (observability only; fix: put LIVE and RECORD into the uncached control page); (3) `ktab` is indexed by
  T in the kernel, by capture bucket in spec C.5 (code, tables, hub doc and model agree, the spec should follow);
  (4) dispatch and combine do not compare their T argument with the header's T; (5) on abort some blocks of combine can
  sum real data while others write NaN (the record is set, the step fails); (6) table values (slot >= 512,
  `n_cold` > 8) are not bounds-checked in the kernel (the plan loader validates them); (7) the 64-entry pinned step ring is
  reused without an event; (8) phases 1 and 6 and the record bit 2 of C.7 are never produced.

## 11. Deviations from the spec and agreements

- Handshake file names use device ids (`srv_<id>.json`), the host abort word at `0xF00` with phase 8, the opcode field in
  the ring entry, the workspace copy in `hx_k_srv_wait`, the strict uncached allocation and the per-layer counters
  (section 3); to be added to Appendix C by the spec owner.
- `freeze-hub` of T5 is a hub that SIGSTOPs itself between two layers (`--freeze-trigger FILE --freeze-layer 5`); it
  exposes the idle-timeout gap above. Plan layer 48 (MTP) is added by hand as hub-only; stripe K=0 lives in
  `runtime.spill_k` (hub owner).
- T1 gate "1 MiB fan-in >= 24 GB/s" is not met: 22.6 GB/s on three V620 senders (section 8.2), 14.5 GB/s on the W7800 with
  four senders (8.6); no change to the gate is proposed here, the spec owner decides.

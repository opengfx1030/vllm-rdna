Decision rule (contract section 8): G0a fail means stay on the two-lane engine. **No-go for building S1-S7 on this tree now.**
The blocker is not the transport: both payload sizes move at 25 GB/s per pair. The blocker is that the decode side does not
reproduce the baseline after a handoff at 8k and 16k, and the cause is not identified. A follow-up with lengths 2048 to 8193
(section "Chunk-count follow-up") refuted the first hypothesis, chunk count: the single-chunk 2048 prompt already deviates,
and P states from one and from two scheduler chunks are bitwise identical at 3073 and 4097. It also showed that the reference
is unstable: the baseline's own prefix-hit run differs from its cold run at four of those five lengths, so "exact tokens and
PPL within 0.02 against one baseline run" cannot separate a transfer error from tail-recompute numerics below 8k. At 8193,
16384 and 16385 the deviation is larger than the baseline's own spread, and at 8193 it depends on how P chunked its prefill;
an overlay of two producers' stores localises that dependence to the recurrent groups 0-3 (GDN conv/ssm and PLE conv), not
to the QSA ring and compressed keys.

Three findings change the contract numbers, all measured:

- The per-rank handoff payload at 16384 tokens is **426.4 MiB** (942 windows, 6 state groups), not the contract's 249.1 MiB;
  at 1024/1025 tokens it is 53.8 MiB. At 64k, linear scaling of the QSA compressed-key group gives about 1.58 GiB per rank
  [INFERENCE].
- A NIXL pull (READ, decode initiated) crosses the root complexes at the same 25.4 GB/s as a push. The audit's "never
  pull across roots" holds for `hipMemcpy` peer reads (6.0 GB/s here, the audit measured 5.7), not for UCX `rocm_ipc`.
- A single-chunk 16k prefill does not fit on a V620 with this recipe: with `max_num_batched_tokens` 17408 the engine boots
  but the 16384-token request raises `torch.OutOfMemoryError` on all four ranks (28 GiB allocated, 0 bytes free), also with
  the KV cache cut to 1.5 GiB. A long prompt can only reach D through multi-chunk prefill in this recipe.

Validity. A cell is INVALID when KFD `evicted_ms` jumps during it. Invalid cells: the NIXL `ipc_only` WRITE 912.1 MiB cell
(12 ms on the destination, in both rounds); in the shared-visible-set cells WRITE 249.1 MiB (12 ms on the destination in both
rounds, plus 10 ms on the source in the second) and READ 912.1 MiB (13 ms on the source, first round only); and both WRITE
cells of the four-pair run (4 to 12 ms on the destinations). The jumps recur on the same cells, and the rates of those cells
equal the rates of the valid ones. Valid cells exist for both directions at both sizes (table above, and READ for the
four-pair run), so the verdict does not depend on the invalid ones. The cause of the evictions was not investigated.

### No host bounce, evidence

- `ipc_only` removes every host RMA transport (`posix`, `sysv`, `cma`); UCX refuses to start without `rocm_copy` (finding 2
  below), which only serves its local mem-type copy endpoint. A put or get of device memory then has one lane, `rocm_ipc`.
- Rate: 25.3 GB/s is the PCIe peer-write rate of the audit (25.2). Host bounce through the same GPUs is 4.8 GB/s and NIXL's
  own host-staged path is 2.7 GB/s. A hidden staging copy cannot run at 25 GB/s through this host.
- With default transports (`UCX_PROTO_INFO=y`, `g0b/nixl_default/src.log`) the protocol table has the row
  `128..inf | rndv using zero-copy read from remote | rocm_ipc/rocm_ipc`; `cma/memory` and `tcp` appear in the worker's
  active-message list and in other tables. The row is the only direct protocol evidence; the measured 25.3 GB/s (against
  2.7 GB/s for the host-staged path) is what shows that no host copy was in the transfer path.
- Both processes saw only their own GPU (`disjoint`): hipIpc and `rocm_ipc` work across disjoint `HIP_VISIBLE_DEVICES`, with
  results identical to the shared visible set.

### First-contact findings (fixed in the spike, relevant to S4)

1. `HSA_ENABLE_IPC_MODE_LEGACY=1` breaks UCX `rocm_ipc`: registration of a 16 MiB torch allocation fails with
   `rocm_ipc_md.c:80 Failed to create ipc ... Address not valid` and NIXL raises `NIXL_ERR_BACKEND`
   (`g0b-first-contact-9b6dde03be/smoke*/src.log`). The default (dmabuf IPC) works. The kernel is the distro one, which has no
   KFD IPC export ioctl [INFERENCE]. Do not set the variable.
2. UCX will not create a worker without a mem-type copy transport: `UCX_TLS=rocm_ipc,posix,sysv,tcp,self` fails with
   `select.c:724 no copy across memory types transport`; `rocm_copy,rocm_ipc,self` fails for lack of an active-message
   transport; `rocm_copy,rocm_ipc,tcp,self` works. Checked on CPU memory and on the GPUs.
3. NIXL READ over `rocm_ipc` is as fast as WRITE cross-root (25.5 vs 25.3 GB/s) while a `hipMemcpyAsync` pull is 6.0 GB/s.
   Likely cause: ROCr runs a device-to-device async copy on the source agent, so both directions are PCIe writes
   [INFERENCE, not verified]. Practical effect: the default NIXL pull mode needs no change to avoid the read penalty.

  at the end of its prefill (a position or rounding offset against the aligned external boundary).

## What the evidence leaves open

Why D differs from the baseline at 8193, 16384 and 16385 by more than the baseline's own variants differ from each other, while
matching the baseline's prefix-hit run bitwise at 1024 and 1025. Hypotheses, none confirmed:

- H1: per-request state that is in no registered region and is read by the QSA kernels at long context (for example
  per-request counters or the sparse indexer's selection state).
- H2 (chunk count, simple form): refuted above. A form tied to the recurrent groups at 4 or more chunks is open.
- H3: the MTP layer's state is incomplete at D (acceptance 0.87 to 0.64 at 16k). Greedy tokens would still match, but a
  different draft pattern changes which positions are verified in multi-token steps and can flip near-ties. This alone does
  not explain the 0.63 logprob delta at 16384.
- H4: the recurrent state D needs (position of the aligned external boundary) differs from the state P holds at the end of
  its prefill, by more as the number of chunks grows. Fits the 8193 overlay, not yet tested directly.

Cheapest next experiments (harness in the branch plus `g0a_hybrid.py`):

1. Dump P's recurrent windows and the baseline's own cached state for the same prompt (a local request on the producer
   server), per group, at 2048 and 8193: shows whether the transferred state equals what the baseline holds, and where they
   differ.
2. P with `MAXBAT=8192` at 8193 (one 8192-token chunk; 17408 did not fit, 8192 may): tests a monotonic dependence on chunk
   count.
3. A likelihood gate instead of free-running greedy tokens (teacher-forced logprob of a fixed 64-token continuation on D
   against the baseline), which removes the near-tie amplification; D with MTP off at 16385 (H3).
4. Real UCX in G0a (`producer_real` arm, not run) and push mode: the stand-in covers READ planning only.

If 1 and 2 do not isolate the cause, treat long-context handoff of QSA/GDN state as not supported in this tree and stay on the
two-lane engine.

## Open decisions D1-D6

- D1 target workload: not decided here. Per-rank handoff is 53.8 MiB at 1-2k and 426.4 MiB at 16k, so short prompts are
  cheap and long prompts are where both the payload and the unresolved correctness problem are.
- D2 ITL gate 70 vs 100 ms: not measured (needs G1).
- D3 MTP hidden: not tested directly. At 1024 and 1025 D reached output bitwise equal to the baseline's prefix-hit path with
  only the transferred caches plus its own tail recompute, so no separate hidden-state transfer was needed there
  [INFERENCE: `_mtp_hidden_buffer` was not inspected]. D's MTP acceptance at 16k (0.62 to 0.64) is below the baseline
  (0.75 to 0.87).
- D4 PLE table (int4 vs shared bf16 mmap, host RAM): not measured; the host-pinned table is still the default, so two
  instances double it unless it is shared.
- D5 prefix caching on D, final state only vs GDN checkpoints: the baseline's own tail-recompute path is not bitwise equal
  to a cold run (1025 and 16385 in the first set; 2049, 3073, 4097 and 8193 in the follow-up, with PPL deltas up to 0.25 and a
  divergence at token 2), so neither a bitwise gate nor "exact tokens, PPL within 0.02" against one baseline run can separate a
  transfer error from tail-recompute numerics below 8k. At 8193 and 16k the deviation exceeds that noise. A gate has to be
  likelihood-based or compare against several baseline variants. Whether final-state-only transfer is enough is open (H4).
- D6 proxy external vs in-process: not decided; the connector flow expects the router to carry `kv_transfer_params`
  (the harness did it in `g0a_requests.py`).

## Limits

- G0a used a file-backed stand-in for the wire (READ semantics). Real UCX registration of the state regions, the real
  handshake, push mode and layer-wise streaming were not exercised in G0a. Real transfers are covered only by G0b, with
  synthetic windows.
- G0b payloads were the contract's sizes (249.1 and 912.1 MiB per rank), not the measured 426.4 MiB per rank with its
  942-window shape.
- Some WRITE cells are INVALID by the eviction rule (listed above); the rates are unaffected.
- The first G0a launch used port 18700, which collided with the soak agent's server; for about two minutes my probe requests
  (short prompts and the PPL probe) reached that server. Those results were discarded; all G0a evidence is from the relaunch
  on port 18741.
- One harness file, `g0_hip.py`, was excluded by the repo's `*_hip*` ignore rule and never committed; it was renamed
  `g0_rt.py` before any evidence run, so every exact-SHA tree contains it.

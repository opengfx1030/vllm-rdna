## Why the arenas exist

[measured: git history and `docs/profiling/`]

1. `docs/profiling/2026-09-08-cudagraph-gdn-root-cause.md`: GDN hybrid output was garbage
   under PIECEWISE capture while dense models were fine. The metadata builder skipped its
   static state-index buffers unless the mode had FULL graphs, so the captured
   `causal_conv1d_update` baked in the address of a per-step `block_table[:, 0]` view; the
   static buffers were also sized by `max_num_seqs`, smaller than the capture ladder.
2. `docs/profiling/2026-09-10-truefull-journal.md` (resolution): at c=8 a decoding request
   still read another request's state page (other requests' prompt text in the output).
   The fix was cherry-picked PR #4: `369773ef7d` / `a589d51c94` "freeze conv/ssm state
   arenas for piecewise cudagraph" (permanent zero-filled `(max_bs+1, *state_shape)` arenas
   per layer, row 0 = NULL, the paged slots gathered into rows 1..n before the decode and
   scattered back after, so the address a graph captures is the arena, never a block-table
   view), then `dd4fb0bcc8` (gather/scatter by decode batch size), `6ffcdecebe` (allocate
   before capture, static-only slots), `74f47b6af9` (assign instead of `register_buffer`).
   Ported to this tree by `e8d1701784` (2026-10-07); `6e56ecb782` keeps the arena layout in
   `update_block_table`; `ad356d1135` sizes the arenas by the decode batch (a 2,049-row
   arena OOMed at load).
3. The underlying hazard is the one `54702c7460` (two-lane, 2026-11-05) fixed for lane D,
   which already keeps RDNA decodes on the paged state without arenas: in mamba align
   mode `block_table_tensor` is a new tensor every step, so a FULL graph that was captured
   with a view of it replays the capture-time address. Staging the indices in the
   builder's own static buffer is all a FULL graph needs.

So the arenas are a safety copy: the decode kernels never needed them. What was missing
for an arena-free decode on the single-lane path is exactly what `54702c7460` added for
lane D: static index buffers. The decode kernels already handle NULL slots
(`gdn_decode_rdna2.cu` L81-92: `state_idx <= 0 || >= num_blocks` writes a zero output row
and touches no state; `long` offsets; `a`/`b`/`mixed_qkv` token strides are launch
arguments, L242-243) and so does the Triton conv update (skips `NULL_BLOCK_ID`).

### The "+4 launches per GDN layer" at c=2

The plan compared the 816 launches of the c=2 "after gdn in_proj_ba" phase with the
theoretical 13 x 48 = 624 of the audit and called the 192 difference "+4 per GDN layer"
and "fills 4". Both are wrong:

+ The c=1 phase measures 672 launches, not 624: 14 per layer, because the out_proj
  activation transform lands in the same phase [measured, `~/w4a8_runs/hi2-tp2/prof/
  hi2-tp2-order/breakdown-fixed.md`, rank 0, trace 3061825]. c=2 minus c=1 in that phase is
  816 - 672 = **+144 = +3 per GDN layer**: the `b`, `a` and `z` copies (rows 8, 9, 15). At
  T=1 the slices of the projection output are dense, so `.contiguous()` / `reshape` are
  views and launch nothing; at T>=2 the token stride is the projection width and each
  copies.
+ The other c=2 launches are in the attention layers: "after attn qkv" 176 -> 240 (+64 =
  +4 per attention layer x 16) and the epilogue 20 -> 21 (+1). 144 + 64 + 1 = 209 =
  2,660 - 2,451 [derived], the whole c=1 -> c=2 difference.
+ Only one of the "fills" is a fill (row 1). The others are the int32 -> int64 index
  casts and the layout copies that `tensor[slots]` / `index_copy_` issue around the
  gather and the scatter (rows 2, 4, 5, 7, 12).

## What the flag changes

`vllm/v1/attention/backends/gdn_attn.py`

+ `gdn_decode_inplace_enabled(vllm_config)`: env `VLLM_RDNA_GDN_DECODE_INPLACE=1` and the
  validated envelope only: the gfx10x HIP kernels (`on_rdna2_hip()`), an fp16 model,
  `VLLM_CAUSAL_CONV1D_RDNA2_UPDATE=0` (the HI2 recipe sets it), none of
  `VLLM_RDNA_GDN_OPAQUE`, `VLLM_GDN_DECODE_RDNA2`, `VLLM_GDN_STRIDED_INPUTS` set to 0, the
  `gdn_decode_rdna2` op built, and no LeapQuant state. Otherwise it logs
  `VLLM_RDNA_GDN_DECODE_INPLACE=1 ignored, the GDN decode keeps its state arenas: <reason>`
  once and nothing changes. The HIP conv update is excluded because it runs a NULL slot
  as an ordinary line, which would write the paged cache's null block; the Triton update
  returns before touching it.
+ `GDNAttentionMetadataBuilder._decode_inplace` (exact class only, so KDA and other
  subclasses keep their metadata). In `build()`, for a pure non-spec decode that fits the
  static buffers, the block-table column 0 (`non_spec_state_indices_tensor`, the same
  source the arena gather used) is copied into the builder's own static buffer with a
  NULL tail, and `non_spec_query_start_loc` into its static buffer; `use_state_arenas`
  stays False and `cache_slot_indices` None. The `block_table_buf` copy that only fed the
  arena gather is skipped. `update_block_table` stages the other KV groups' slots into
  their own builder's buffer also under PIECEWISE-only configs when in place (flag off:
  unchanged).

`vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py`

+ `__init__`: `_rdna_decode_inplace`; the arenas are not allocated when it is set.
+ `forward_cuda`: `core_attn_out` is `torch.empty` instead of `torch.zeros` when
  `_decode_step_in_place` (flag, strided decode inputs, no LeapQuant, no spec rows, no
  prefill, `num_actual_tokens == num_tokens`, HIP decode available): the HIP decode writes
  every row (a zero row for a NULL slot). The gated norm gets z at its token stride
  (`_gated_norm_strided_z` calls `_rocm_C.gated_rms_norm` with the `[T, HV, V]` view; same
  kernel and values, one launch less; a one-time probe, never run during capture, falls
  back to `norm(x, z)`).
+ `_forward_core_decode_non_spec`: `b`/`a` `.contiguous()` skipped (the kernel takes their
  token strides); the state is the paged cache (`_bind_decode_state_arenas` already
  returns it when `use_state_arenas` is False).

Not touched: `layernorm.py` (the gated-norm z flatten stays for every other caller), the
prefill `final_state = torch.zeros_like(initial_state)` (prefill side: one 1.5 MiB memset
per prefill sequence per layer per chunk, about 0.2 ms per 2048-token chunk against
seconds [derived]; not worth a prefill change in a decode slice).

## Proof

Everything below ran on HIP 4 under the flock. The harness
(`tests/kernels/mamba/gdn_glue_harness.py`) builds the real GDN layer class with the HI2
per-rank shapes (HV=24, H=8, K=V=128, conv width 4, fp16, 2 MiB pages, conv and ssm as
two strided views of one uint8 page tensor), the real metadata builder and the real
`forward_cuda` / `_output_projection`; only the three projections are stand-in fp16
matmuls. Two rigs (flag off = arena, flag on = in place) share the random weights and
state.

arena builder's gather reads); MTP-verify batches, a batch with a row that did not draft,
and mixed prefill + decode batches get the same metadata field for field with the flag on
and off (they never used the arenas); non-first KV groups stage their own buffer under

Existing GDN tests (`test_gdn_output_projection.py`, `test_gdn_decode_rdna2.py`,

(CuteDSL needs a CUDA SM10x GPU).

**One intended difference, padded rows.** The builder counts the V2 runner's zero-length
padding requests as decodes (`num_decodes` = the padded batch, e.g. 4). The arena path
decodes those rows as if real, against page 0 (the NULL page): it gathers page 0, decodes,
and scatters back, so the padded rows' outputs are garbage and page 0 is rewritten (up to
three writers racing for the same page). The in-place path writes zero rows and never
touches page 0. Real rows and every other page are bit-identical; nothing reads the
padded rows' outputs or page 0.

### Time [measured, shared box]

+ 48-layer FULL-graph replay (`gdn_glue_profile.py timing`, `timing-nothrash.log`,
  `timing-thrash64.log`): in the result table. Hot = the state of 16 blocks per layer stays
  in cache; thrash = a 64 MiB tensor is read after every layer, which approximates the
  engine where each layer's weights evict the state. Repeats agree within 0.3 us per layer.
+ The replay saving is not the sum of the per-kernel savings (c=1: replay -61.5 us per
  layer against 51.9 us of kernel time; c=2: -56.3 against 60.2): the eager medians and the
  graph replay do not see the same cache state. The replay table is the headline.
+ Isolated `gdn_decode_rdna2` (`gdn_glue_profile.py kernel`), us warm / cold, arena-style
  1.5 MiB row stride against the paged 2 MiB page stride:
  c=1 6.68 / 9.68 vs 6.72 / 9.72; c=2 10.84 / 14.88 vs 10.80 / 14.96;
  c=4 19.38 / 29.74 vs 19.40 / 26.30; c=8 34.12 / 40.22 vs 34.16 / 40.52. A set of other
  slots (5+7i) is the same, so the kernel is not slower on the paged layout.

## Risks and what is not proven

+ Not run end to end here (HIP 4 slice); the scoreboard arm `gdnglue` did, see the status
  note: ITL and quality of the real model are measured there.
+ MTP: spec-verify batches never used the arenas (`use_state_arenas` is only set for a
  pure non-spec decode), so the flag leaves their metadata unchanged (builder test
  `test_other_steps_keep_their_metadata`, field for field) and the spec kernels are not
  touched. The slice ran MTP=0; the arm `final-mtp2` (the flag, MTP=2) passes the probes.
+ Prefix caching (mamba align mode): the GPU bit-exact tests in `align` mode put each
  request's state in a later block of its table (columns 1 to 6) and the real builder
  selects it (`mamba_get_block_table_tensor`, upstream of the staging copy and the same
  source the arena gather used); the builder test checks that the staged slots equal the
  arena builder's. Arm `gdnglue` ran a server with prefix caching: its prefix-cache probe
  passes (cold 4.74 s, warm 0.41 s, hit rate 96.2%); evictions and copies of the state block
  under cache pressure were not exercised.
+ The flag only helps pure non-speculative decode; mixed and prefill steps are unchanged.
+ The Triton conv update JIT variant for the in-place state strides compiles during the
  engine's warm-up/capture, before any graph is captured; the harness exercises it at
  capture time too, but the first server start with the flag is the real check.
+ `empty` for `core_attn_out` relies on the HIP decode writing every row and on
  `num_actual_tokens == num_tokens`; otherwise the zero fill stays.
+ Outside the envelope above (LeapQuant, non-fp16, non-gfx10x, HIP conv update, strided
  decode off) and for builder subclasses the arenas are kept, with a one-line warning.
+ int32 slot indices: the kernels use 64-bit offsets (tested past 2^31 elements).
+ Harness caveats: stand-in GEMMs (rocBLAS, 18-78 us), cache thrash by a 64 MiB read.

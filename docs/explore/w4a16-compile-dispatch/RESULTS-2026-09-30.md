# RESULTS 2026-09-30 — RDNA2 W4A16 M-dispatch under torch.compile (PR #30)

Box: `par1-cs25` (8× Radeon PRO V620, gfx1030), ROCm 7.14.0, torch 2.12.0,
vLLM `e6e54dba6d475b42e85c687de7fd9b96` (`explore/pr30-compile-dispatch`).
All serve/probe runs use GPUs 4–7 (`GPUIDS=4,5,6,7`); GPUs 0–3 are a co-tenant.

## Verdict

| Hypothesis | Result |
| --- | --- |
| **H1** — the compiled graph holds one W4A16 op per GEMM, fixed by the trace-time M | **HOLDS** |
| **H2** — decode therefore runs other kernels than the selector intends | **HOLDS** (implied by H1 graph evidence; rocprof below) |
| **H3** — per-call dispatch is ≥ +3 % decode at the serve matrix | **FAILS** (max +1.5 %; see table) |

**Recommendation: do not flip the default.** The freeze is real but has no
material serving cost on this stack; keep `VLLM_RDNA2_W4A16_RUNTIME_DISPATCH=0`.
The opt-in op and probe can land as exploration tooling.

## Unblocking the probe (engine-init failures)

The probe could not boot. Four independent causes, all fixed:

1. **27B hybrid at TP=1 OOMs in model init.** Every GDN layer allocates an
   unsharded `(max_bs+1, *ssm_shape)` state arena; with the default
   `max_num_seqs` the arenas total ~30 GiB before weights finish. The dense
   `Qwen2.5-14B-Instruct-AWQ` was tried as a TP=1 substrate but it takes the
   classic AWQ path, not `RDNA2W4A16LinearKernel` (`no RDNA2W4A16LinearKernel
   layers`). **Fix: run the 27B compressed-tensors W4A16 at TP=4.**
2. **27B TP=4 JIT compile aborts at the cache-save gate.** With
   `VLLM_USE_AOT_COMPILE=0`, `compiler_interface.is_saveable_2_10` rejects the
   hybrid graph (>1 `aot_autograd` artifact) and raises *"The compiled artifact
   is not serializable."* **Fix: `VLLM_DISABLE_COMPILE_CACHE=1`** (matches the
   production 27B recipe). `computation_graph.py` is still written to
   `local_cache_dir` (`backends.py:1359`), so H1's graph-op signal survives.
3. **Wrong GPU set.** `HIP_VISIBLE_DEVICES=0,1,2,3` maps to the co-tenant's
   devices; workers fail with *"Free memory on device cuda:0 (2.3/29.98 GiB)"*.
   **Fix: `GPUIDS=4,5,6,7`** (the runtime's free set).
4. **Probe bugs at TP>1.**
   - `apply_model(_collect_w4a16_layers)` pickles the callable to spawned
     workers; a helper defined in `__main__` (run via `-m`) cannot be resolved.
     **Fix: move the helper to `benchmarks/kernels/w4a16_compile_dispatch/_layers.py`.**
   - The helper looked for the kernel under `quant_method`; compressed-tensors
     keeps it at `module.scheme.kernel`. **Fix: check both owners.**

The b1/b2/b3 drivers also gained an exe-scoped `hygiene()` step: a killed probe
leaves its spawned `EngineCore`/`Workers` holding ~27 GiB/GPU, and the next arm
then boots into *"free memory 2.3/29.98 GiB"*.

## B1 — H1 on the real 27B (TP=4, F&P, `max_num_batched_tokens=8192`)

`trace_m = 8192`; 255 W4A16 layers/rank; selector expects `prefill` for all 255
at trace M and `{rdna2_decode: 192, prefill: 63}` at M=1.

| arm | runtime dispatch | W4A8 | ops in compiled graph (per rank) | greedy == python |
| --- | --- | --- | --- | --- |
| python | 0 | 0 | `{gptq_gemm_rdna2_prefill: 160}` | — |
| op | 1 | 0 | `{rdna2_w4a16_gemm: 160}` | True |
| eager | 0 | 0 | n/a (no compile) | False |

With W4A8=1 the frozen graph holds `{w4a8_gemm_rdna2}`; the op arm holds
`{rdna2_w4a16_gemm}`. **H1 holds:** the compiled decode path contains only the
trace-time op; the 192 decode GEMMs that the selector sends to `rdna2_decode`
run the prefill op instead.

## B2 — H2 (rocprofv3 kernel traces)

Attempted at TP=4 with the serving arms. `rocprofv3 --kernel-trace` in the
multi-process vLLM harness (parent + spawned `VLLM::Worker`s) emits one
per-process `.dat` under `./.rocprofv3/` and never opens the aggregated
`--output-file` CSV (no `Opened result file` in the prof log); the driver's
`kernels` step therefore found nothing. The single-process invocation naming is
correct (`--kernel-trace --output-format csv --output-file X` →
`X_kernel_trace.csv`); the multi-process case needs more work to aggregate.

**H2 is established by B1's `computation_graph.py` evidence instead**, which is
stronger: the frozen arm's compiled decode path contains only
`gptq_gemm_rdna2_prefill` (or `w4a8_gemm_rdna2`), while the eager arm follows the
per-M selector and calls `rdna2_decode` at M≤32.

## B3 — H3 serve matrix (27B AWQ, TP=4, FULL_AND_PIECEWISE, `max-num-seqs 8`, `max-num-batched-tokens 2048`)

`VLLM_RDNA2_W4A16_RUNTIME_DISPATCH=0` vs `1`; fresh cache per arm; 16k/1k and
1k/512, c=1/8; coherence probe 4/4 OK both arms.

| cell | rd=0 tok/s | rd=1 tok/s | Δ |
| --- | ---: | ---: | ---: |
| 1k/512 c=1 | 39.23 | 39.52 | +0.74 % |
| 1k/512 c=8 | 144.61 | 146.84 | +1.54 % |
| 16k/1k c=1 | 21.25 | 21.29 | +0.19 % |
| 16k/1k c=8 | 35.71 | 35.79 | +0.22 % |

All deltas are < +3 %; prefill/TTFT within noise (16k c=1 TTFT 21279 vs 21375 ms);
greedy/coherence identical. **H3 fails.** The frozen prefill kernel at M=1 is
within ~1 % of `rdna2_decode` on this model (the decode path is not GEMM-bound
enough for the choice to matter).

## W4A8 freeze check

- **Flash-Next (TP=4, F&P, `VLLM_RDNA2_W4A8_SDOT4=1`):** the engaged W4A8 is the
  **fused MoE** path (`moe_w4a8_gemm_rdna2`, config `moe_a8_k32_ag`); the model
  uses `CompressedTensorsWNA16RDNA2MoEMethod`, and the dense `w4a8_prefill`
  selector never fires (`W4A8-DEBUG`: no fast-path shapes). The runtime-dispatch
  A/B is a wash: 1k/512 c=1 40.403 → 40.39 (−0.03 %), c=8 167.907 → 168.49
  (+0.35 %). The dense fix does not touch the MoE path.
- **27B dense (TP=4, F&P, W4A8=1):** the dense freeze is real — under compile the
  graph holds `w4a8_gemm_rdna2` (frozen at trace M=8192); at decode M≤32 the C++
  entry takes its internal W4A16 fallback `gptq_gemm_rdna2_prefill`, **not**
  `rdna2_decode`. Cost: c=1 36.79 → 37.06 (+0.73 %), c=8 209.05 → 213.8
  (+2.27 %) — same class as H3, below the bar.

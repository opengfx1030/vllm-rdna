# WNA16 tile8 threshold, HIP 2–5 serving A/B

On 2026-10-23, four serial uninstrumented arms compared the original WNA16 FP16 MoE tile8 threshold (`num_tokens >= 4096`) with the candidate (`>= 1024`). Arm order was original, candidate, candidate, original. Each arm ran 1024/512 and 16384/1024 at c1 (8 requests) and c8 (32 requests), using the same Qwen3.8 Flash-Next AWQ target, INT4 PLE, native MTP2, target MonoKernel, TP4/EP4, fixed KV budget, `LPTH=1024`, prefill interval 2, seed, corpus, temperature 0 and output lengths. The MTP Mono drafter was disabled in every arm. Prefix cache was reset successfully before all 16 timed cells. All arms used boot `76e1e680-59ae-474d-bef7-ddeee7d5ca4d` and binary SHA-256 `6e8e486e548213d159236298a24b0f9ffbc18e49ccc234dcace7e8c1d59f4df3`.

Numbers are means of the two arms per variant. `prefill tok/s/request` is mean input tokens divided by mean TTFT; it is not whole-run input throughput. Across all four timed cells, the fixed 696,320 input and 61,440 output tokens took a mean 694.33 s for original and 680.67 s for candidate, so whole-run input and output throughput were both +2.02%. The candidate improved c1 prefill and TTFT in both prompt lengths beyond the original run-to-run spread. It did not improve c8 prefill/TTFT. c8 decode and aggregate output improved, but acceptance length also rose; this A/B does not isolate a decode-kernel gain from output-path variation. Long c1 decode and acceptance varied more between repeats than between variants.

Acceptance length is a useful efficiency/quality measure: more accepted draft tokens usually mean fewer target verification rounds per emitted token, which can improve decode throughput. It is not a standalone speed metric; target verification cost, scheduling, and workload mix still matter. Here acceptance rose in both c8 cells (2.041→2.169 short, 2.181→2.233 long) and fell in both c1 cells (2.008→1.998 short, 2.379→2.344 long). The c8 decode gains therefore cannot be attributed to tile size alone, and c1 acceptance shows a small regression.

All 16 benchmark cells completed with zero failed requests and saved detailed request intervals/text. Greedy, PPL (4.81–4.85), prefix (8.6–8.7×), normal-EOS concurrency (0 hard failures/48 per arm), after-load parity and response health gates passed. Concurrency near-tie/soft warnings were present in both variants. Repeated same-source arms matched only 1/80 original and 2/80 candidate full generated texts by request index; cross-source pairs matched 0/80 and 1/80. Output differences are therefore not candidate-specific evidence of a correctness regression. The benchmark saves generated text but no first-token logprobs, so it cannot classify every text divergence numerically.

Arm 02 triggered the strict dmesg gate after completing its timed cells: one corrected PCIe BadTLP on AMD root port `0000:40:03.1` at about 13:31:31 CEST (correctable status `0x40`, uncorrectable status `0`, Data Link Layer). The kernel reported correction; there was no amdgpu VM/page/HSA fault, reset, or serve fault. The original driver stopped; after classification and idle/source checks, arms 03–04 resumed with a gate that aborted on any new dmesg event. They had zero new events. This host event remains a caveat for arm 02.

Source and binary hashes matched before and after every arm. Original dispatcher SHA-256 was `35bbb4b074f78eab69a1ddd028ab5be679798cf2390b9e38041bd49c445772f9`; candidate was `38470e95fdb21affd4d045ec113a6928e3489bbc8bdec2e270c03539611cdebb`. The same port 18884 was reused **serially** in all arms because the wrapper's idle-check loop overwrote its shell `port` variable; every server was stopped and checked idle before the next source swap. Final audit found the candidate dispatcher restored, binary unchanged, same boot, no KFD processes, no listener on 18884, and zero V620 VRAM usage. No additional serving runs were launched.

The four local arm directories retain raw JSON, logs, and full responses. The committed evidence keeps the derived numeric CSVs, concise configuration and provenance manifests, and parity-test output; it omits response text and bulky request-log captures. The CSVs were derived from saved JSON by `analyze.py`.
